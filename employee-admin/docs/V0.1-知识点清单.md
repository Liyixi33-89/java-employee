## 1. 知识点总览

### 1.1 为什么要把「有」拆成五级

原来的三档（✅ / ⚠️ / ❌）太粗：它把三件完全不同的事混成了一个 ✅。

- **`Employee` 里的 `toString`**：代码有，但文档从没讲为什么重写 → 学习者说不出理由
- **`EmployeeService` 里的排序**：代码有，文档讲了、缺口清单也讲了 → 学习者能解释
- **`BasicsDrill` 里的短路行为**：有练习能跑能改 → 学习者能动手验

这三项都标 ✅，但学习者的实际状态差了一个量级。所以覆盖要按**证据**分级，
判定条件必须客观可查，不能靠感觉。

### 1.2 五级判定（维度一：内容覆盖）

| 级别 | 名称 | 判定条件（三条同时满足） | 学习者当前能做到 |
|---|---|---|---|
| **S** | 可自证 | ① 生产代码用 ② 文档讲原理 ③ 有可跑练习或断言 | 能读懂、能改参数看变化、能解释为什么 |
| **A** | 有讲解 | ① 生产代码用 ② 文档讲原理 | 能读懂、能定位、能解释大意 |
| **B** | 仅使用 | 只有「生产代码用了」，**没有专门讲解** | 能认出，但说不清为什么这么写 |
| **C** | 仅示例 | 只在练习文件里，主程序没用过 | 跑过，但没见过真实业务用法 |
| **❌** | 未覆盖 | 完全没有 | — |

**证据标签**（每行最后一列，可组合）：

| 标签 | 含义 | 怎么查证 |
|---|---|---|
| `P` | 生产代码真的调用 | 在 `src/` 非练习文件中能搜到 |
| `D` | 文档有专门段落讲「为什么」 | 导读或本清单有对应小节 |
| `E` | 有独立可跑练习 | `BasicsDrill` / `OopDrill` / `ErrorDrill` |
| `T` | 有场景断言验证 | 被 `run-samples.ps1` 覆盖 |

> **关键规则：S = P + D + (E 或 T)。缺 D 的一律降到 B。**
>
> 这条规则的作用：把「代码里有」和「讲清楚了」强行分开。
> 大量知识点被生产代码用着，但没人解释过为什么——那不算学会，只是照抄过。

### 1.3 另一个维度：本阶段要求

| 标记 | 含义 |
|---|---|
| 必会 | 要能独立写出来、能解释 |
| 理解 | 能读懂、能说清为什么，不必默写 |
| 后续 | 本阶段只要求知道有这个东西 |

> **两个维度必须分开看**：
> - 「S 级 + 理解」→ 状态很好，不用花时间
> - 「B 级 + 必会」→ **这是真正要补的地方**，见 §1.10 的 B 级待补清单
> - 「C 级 + 后续」→ 正常，V0.2 再深入

## 2. 逐点详解（只展开容易误解的）

### A1—A5 编译与运行链路

```powershell
javac -encoding UTF-8 -d out src\*.java      # build.ps1:10
java -Dstdout.encoding=UTF-8 -cp out Main    # build.ps1:14
```

- **JDK ⊃ JRE ⊃ JVM**：JDK 带编译器 `javac`，JRE 只是运行环境，JVM 是执行字节码的虚拟机。你装了 JDK 所以两样都有。
- **`-d out`**：指定输出目录，同时决定包的目录结构。类在默认包时直接落在 `out/`。
- **`-cp out`**：classpath，JVM 找类的根目录。`Main` 不带 `.class`。
- **为什么有中文参数**：`-encoding UTF-8` 让编译器按 UTF-8 读源码；`-Dstdout.encoding=UTF-8` 让运行时按 UTF-8 写控制台。缺任一个都可能乱码。

> 自证：把 `-encoding UTF-8` 删掉再编译，看是否报 "编码 GBK 的不可映射字符"。这是最常见的第一个坑。

### A6 包与 import（⚠️ 部分覆盖）

当前 5 个类**全在默认包**（没有 `package` 声明），所以互相引用不需要 `import`。
只有 JDK 的类需要：`import java.util.Scanner;`。

**这在本阶段是合理的**，但必须知道默认包有硬限制：**默认包里的类不能被其他包的类引用**。V0.2 拆分层（`domain`/`service`/`ui`）时必须加 `package`。

`import` 规则：只有 `java.lang` 自动导入（`String`、`System`、`Integer`、`Math`），其余一律手写。

### B2 三种变量

| 种类 | 例子 | 生命周期 |
|---|---|---|
| 静态变量 `static` | `ConsoleMenu.java:13` `LINE` | 类加载时创建，全局一份 |
| 实例变量 | `ConsoleMenu.java:20` `running` | `new` 时创建，每个对象一份 |
| 局部变量 | `ConsoleMenu.java:128` `Employee existing` | 方法执行时创建，出方法即销毁 |

`LINE` 为什么是 `static`：所有菜单对象共用同一个常量，没必要每个对象存一份。

### B3 `final` 的三种含义

```java
public final class Employee {              // ① 类不可被继承
    private final String employeeNo;       // ② 字段只能赋一次值
    private static final String LINE = ...; // ③ 常量（static + final）
```

项目里 `employeeNo` 用 `final` 是**业务决策**，不是语法练习：工号是外部业务标识，改了历史记录就对不上。所以完全没有 `setEmployeeNo`。

### B7 `switch` 箭头语法

```java
switch (choice) {
    case "1" -> handleCreate();
    case "0" -> running = false;
    case ""  -> out.println("输入为空，请输入 0-8 之间的数字。");
    default  -> out.println("无效选项：...");
}
```

老写法 `case "1": handleCreate(); break;` 漏 `break` 会"穿透"到下一个 case。箭头写法没有这个问题。

注意 `case ""` 单独处理空串 —— 这是 **T05「处理非数字菜单」** 的落点。空串既不匹配 `"1"` 也不该归入 `default`，因为给用户的提示不同。

### B18 编码三件事（项目里踩过真实坑）

```java
// Main.java:12  Scanner 指定 UTF-8 解码
new Scanner(System.in, StandardCharsets.UTF_8)

// ConsoleMenu.java:224  清理不可见字符
raw.replace("\uFEFF", "").replace("\u200B", "").trim()
```

三个概念必须分清：

| 概念 | 是什么 | 在本项目的表现 |
|---|---|---|
| UTF-8 | 字符 ↔ 字节的映射规则 | 中文"张三"占 6 字节 |
| BOM | 文件开头标记 `EF BB BF`，解码后是 `\uFEFF` | 从网页粘贴 `1` 变成 `"\uFEFF1"`，被判非法 |
| 零宽字符 | `\u200B`，看不见但存在 | 同上，肉眼无法发现 |

**这就是为什么 `normalize` 不只 `trim()`**。纯 `trim()` 只能去掉空格、Tab、换行，去不掉 BOM。

### C7—C8 `equals` 与 `hashCode` 的契约

```java
if (!(o instanceof Employee other)) {   // ① 类型不对
    return false;
}
return employeeNo.equals(other.employeeNo);  // ② 只比工号
```

```java
return Objects.hash(employeeNo);        // 必须用同样的字段
```

**硬性契约**：两个对象 `equals` 为 `true`，`hashCode` **必须**相等。违反会导致 `HashMap`/`HashSet` 找不到本该找到的元素。

本项目用 `Map<String, Employee>` 以 String 为键，所以 `Employee.hashCode` 其实没被用到。**那为什么还写**：一旦有人把 `Employee` 放进 `HashSet` 就会出现诡异 bug。这是"按意图写代码"，不是多余。

另一种写法 `Objects.equals(a, b)` 更安全（两侧都可能为 `null` 也不炸）。

⚠️ **注意本项目的事实**：`Employee` 的构造方法**没有做任何校验**，它不保证工号非空。
校验发生在服务层 `EmployeeService.requireEmployeeNo`——也就是"只有走服务层创建才安全"。
如果有人绕过服务层直接 `new Employee(null, null)`，`equals` 里的 `employeeNo.equals(...)` 会抛 NPE。
这是**当前设计的一个真实弱点**（靠调用约定而非类型/构造保证），V0.2 可以考虑在构造方法里加校验。

### C11 模式匹配 `instanceof`

```java
if (!(o instanceof Employee other)) {
    return false;
}
// 这里 other 已经是 Employee 类型，不用强转
```

Java 16+ 写法。老写法要先判 `instanceof` 再 `(Employee) o` 强转，容易写错。

### C16 依赖注入（为什么不是 `new` 在内部）

```java
// Main.java:13-14   在外部造好，传进去
EmployeeService service = new EmployeeService();
ConsoleMenu menu = new ConsoleMenu(scanner, System.out, service);
```

对比反面写法：

```java
public class ConsoleMenu {
    private final EmployeeService service = new EmployeeService();  // ❌ 自己造
}
```

区别在于**谁决定用哪个实现**。外部传入时，V0.2 可以传「文件版 service」，`ConsoleMenu` 一行不用改；自己造则写死了。

这个模式叫**依赖注入**，是后面 Spring 的核心思想。现在用构造参数实现，不用框架。

### D2 为什么 `LinkedHashMap` 而不是 `HashMap`

```java
private final Map<String, Employee> store = new LinkedHashMap<>();
```

| 实现 | 顺序 | 本项目 |
|---|---|---|
| `HashMap` | 按 hash，看起来是乱的 | ❌ 列表顺序不可预期 |
| `LinkedHashMap` | 保持插入顺序 | ✅ 列表按新增次序展示 |

菜单 2「员工列表」要按新增顺序显示，所以必须 `LinkedHashMap`。

### D10 防御性拷贝

```java
public List<Employee> findAll() {
    return new ArrayList<>(store.values());   // new 一份副本
}
```

如果写 `return (List<Employee>) store.values();` 或直接暴露内部集合，调用方 `list.clear()` 就会**清空内部数据**。`new ArrayList<>(...)` 复制一份，外部怎么改都不影响 `store`。

> 注意：这是**浅拷贝** —— 复制的是引用的列表，元素还是同一个 `Employee` 对象。调用方改 `employee.setName(...)` 仍会影响存储。要彻底隔离需深拷贝（本阶段不需要，`updateName` 就是走对象引用修改的）。

### D11 遍历时修改集合（未覆盖，但要知道）

```java
for (Employee e : store.values()) {
    store.remove(e.getEmployeeNo());   // ❌ ConcurrentModificationException
}
```

本项目**恰好没有这个写法**（删除走 `requireExisting` + 单独 `remove`，不在遍历里）。但这个坑必须知道。

### E3 受检 vs 非受检

```java
public class BusinessException extends RuntimeException {   // 非受检
```

| 类型 | 父类 | 编译器强制 catch | 适用 |
|---|---|---|---|
| 受检 | `Exception` | 是 | 外部环境问题（文件、网络） |
| 非受检 | `RuntimeException` | 否 | 编程错误、业务规则违反 |

选非受检的理由：业务规则违反（工号重复）不该强迫每一层调用都写 `throws`，否则代码被 `throws` 声明淹没。V0.2 的 `IOException` 则是受检的，那时你会看到区别。

### G1 怎么练

### G6 落地时踩到的真实坑（重要）

`DateTimeFormatter.ofPattern("yyyy-MM-dd")` 默认是 `ResolverStyle.SMART`，
会把**不存在的日期静默修正**：输入 `2024-02-30` → 成功创建 `2024-02-29`。
用户看到"新增成功"，数据却错了 —— 这正是最阴险的静默错误。

修复（`Employee.java:25-26`）：

```java
DateTimeFormatter.ofPattern("uuuu-MM-dd").withResolverStyle(ResolverStyle.STRICT)
```

两个细节缺一不可：
- `STRICT`：越界日期直接抛 `DateTimeParseException`，被翻译成"日期格式错误"
- `uuuu` 而非 `yyyy`：STRICT 下 `yyyy` 表示「纪元年」，缺纪元信息会解析失败；`uuuu` 是纯年份

验证结果：`2024-02-30` 被拒绝，`2024-02-29`（闰年真实存在）通过。

### G5 自己练

```java
for (Employee e : store.values()) {
    if (e.getName().equals("张三")) {
        store.remove(e.getEmployeeNo());   // ❌ 遍历中改集合
    }
}
```

**正确理解（常见误区）**：

| 说法 | 准确性 |
|---|---|
| 遍历中修改集合一定抛 `ConcurrentModificationException` | ❌ **不一定** |
| 遍历中修改集合**可能**抛，且结果不可预期 | ✅ 准确 |

`ArrayList`/`HashMap` 的迭代器是 **fail-fast** 的——它只是"尽力"检测到修改就抛，
**不是保证**。以下情况下可能不抛，但数据已经错了：

- 集合很小时修改位置恰好没被检测到
- 用 `HashMap` 删除了一个"已经遍历过"的键

而且 fail-fast 是 `java.util` 实现的选择，**不是 Java 语言规定**。
`ConcurrentHashMap` 的迭代器就是弱一致的，遍历中修改不抛异常，但也不保证看到新数据。

**结论：不要依赖"它会不会抛异常"来判断代码对不对。** 遍历中不要改集合，这是纪律。

改法二选一：
1. 收集待删工号到 `List`，循环结束后批量 `remove`
2. 用 `Iterator` 的 `remove()`（唯一允许的遍历中删除方式）

### G3 留到 V0.2 的理由

接口的价值在于「同一份业务代码，换一种存储实现」。现在只有内存一种实现，
硬写接口会是空壳（一个实现配一个接口 = 无意义抽象）。V0.2 加文件存储时，
第二个实现出现，抽象才有价值。**这是"不要提前抽象"的实例。**
